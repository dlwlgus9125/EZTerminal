# 단계별 AI 프로필과 Orca 기반 팀 운영

상태: **ai-operating-01 · r6 승인 기준에 포함** ([승인 기록](APPROVAL.md)). 제품 구현·AI 실행·모델 설정 저장을 수행한 문서가 아니다. [브라우저에서 보기](index.html#ai) · [역할별 프롬프트 원문](AI-PROFILES.md).

## 현재 설계와 이번 보강

기존 설계에는 대표 AI, 관리형 작업자, 분리된 작업 사본, 검토와 로컬 통합이 있었다. 단계마다 사용할 프롬프트·모델·도구·문맥의 조합과 팀 운영 모드는 충분히 정의되지 않았다. 현재 제품에는 세션의 provider·model·permission 선택이 있지만, 그것이 아래 단계별 프로필 시스템의 구현을 뜻하지 않는다.

이 보강안은 **업무 단계에 맞는 AI 프로필**을 정하고, **누가 어떤 방식으로 함께 일할지**를 팀 설정으로 분리한다. 같은 모델이 여러 역할을 맡거나, 각 역할을 다른 제공자·모델에 맡길 수 있다. 모든 화면에 별도의 AI를 상주시킬 필요는 없다.

화면을 열거나 스킨을 바꾸면 AI가 실행되는 것이 아니다. 새 요청, 명시적으로 시작한 팀 실행의 배정, 허용된 자동화만 실행 계기가 된다. 상태 확인·설계 확정·터미널 사용·PC 제어처럼 사용자나 호스트가 수행하는 단계에는 AI 자동 실행을 붙이지 않는다.

## Orca에서 확인한 기능과 EZTerminal의 적용

확인일: 2026-10-12. 공식 문서에서 확인한 동작을 요약했다. 아래 적용 방식은 EZTerminal 제안이며 Orca와 동일한 구현 또는 모든 환경에서의 지원을 뜻하지 않는다.

| 확인한 Orca 기능 | EZTerminal에 반영할 방식 |
| --- | --- |
| 작업자별 model·effort, 요청/적용 설정 기록, 작업·배정·메시지·질문 | 역할별 설정과 실행 시도 기록, 대표 AI의 질문함, 중복·늦은 결과 구분 |
| 같은 요청을 독립 작업 공간에서 수행해 결과 비교 | 같은 기준·수용 조건으로 후보를 만들고 D19에서 채택 |
| 세션의 모델 선택과 구조화 대화 | 대화 스킨과 무관한 모델·프롬프트·도구 설정 |
| 작업별 worktree | 구현의 파일·브랜치·미리보기·검증 위치 분리 |
| 완료·질문·대기 feed | 기존 D16 작업 화면과 D27 받은 요청에 모아보기 |

근거: [Orca Orchestration](https://www.onorca.dev/docs/cli/orchestration), [병렬 비교](https://www.onorca.dev/docs/recipes/parallel-agents), [Native Chat](https://www.onorca.dev/docs/agents/native-chat), [Worktrees](https://www.onorca.dev/docs/model/worktrees), [Agents Feed](https://www.onorca.dev/docs/activity).

Orca의 Run은 작업·메시지를 묶는 단위이며 그 자체가 자동 스케줄러는 아니다. EZTerminal은 기존 호스트가 선행조건·실행 슬롯·상태 전이를 판단하도록 확장한다. 단계별 제품 기획 프롬프트와 기획 권한 경계도 EZTerminal이 추가로 설계하는 부분이다.

I01–I11은 사용자 확정 완료다. [프로필 편집·AI 제안·재시도·모델 장애의 동작 계약](POLICY-CONTRACTS.md)과 [정책별 예상도](index.html#policies)를 따른다. AI 프로필 제안은 변경 전후·이유를 확인해 적용해야 새 버전이 된다. 전체 화면 승인은 별도다.

기본 프로필 → 프로젝트 프로필 → 이번 작업에서 명시한 설정 순서로 구체화한다. 상위 정책이 허용하지 않은 권한은 하위 설정으로 넓힐 수 없다. 프로젝트에 있는 임의 텍스트나 작업자의 메시지도 호스트 정책을 바꿀 수 없다.

## 모델 선택과 변경

기본 동작은 사용자가 연결한 AI를 상속하고 역할별로 변경할 수 있게 하는 것이다. 모델의 최신 이름이나 가격을 고정하지 않는다. 제공자 실행 PC가 보고한 모델·지원 옵션을 기준으로 선택한다. 기획 자료에는 실제로 연결되지 않은 모델을 사용 가능·최적·저렴하다고 표시하지 않는다.

- 요청 provider/model/options와 실제 적용 provider/model/options를 실행 전후에 분리해 보여 준다. 확인되지 않은 값은 미확인으로 남긴다.
- 특정 모델의 지원 여부를 확인할 수 없으면 실행 준비의 설정 필요 상태로 둔다. 필요한 설정을 무시하거나 다른 제공자로 자동 바꾸지 않는다.
- 추천 프로필은 수정 가능하다. 같은 모델을 모든 단계에 사용할 수도 있고, 예를 들어 대표·구현·검토에 서로 다른 AI를 지정할 수도 있다. 특정 브랜드의 역할 우위를 전제로 하지 않는다.
- 실행 중 바꾸려는 설정은 새 실행·새 attempt부터 적용한다. 현재 실행의 지시·결과 기록은 변경하지 않는다. 지원되는 중단·설정 변경 절차를 명시한다.
- 다른 제공자로 넘길 때는 목표·결정·관련 산출물·미해결 질문을 인계한다. 제공자 내부 세션이나 비공개 추론이 그대로 이동한다고 가장하지 않는다.
- 인증은 기존 provider 연결을 사용한다. 프로젝트 프로필에는 비밀값을 저장하지 않으며, PC별 모델 binding·인증 참조와 공유 가능한 역할 템플릿을 구분한다.
- 사용량을 제공하는 경우 관측된 값을 표시한다. 가격·토큰 값이 없으면 비용 상한을 보장한다고 하지 않고 동시성·검증 재시도처럼 합의한 제한만 적용한다. 전체 실행 시간으로 중단하지 않는다.

## 프롬프트 조립과 인계

1. 단계와 권한: 기획/실행, 허용 도구, 변경 위치, 검토 조건.
2. 프로젝트 지침: 사용자가 정한 제약, 현재 계약, 언어·품질 기준.
3. 역할 프롬프트: 선택한 프로필 버전.
4. 현재 과업: 목적·범위·완료 조건·담당·작업 및 시도 ID.
5. 참조 묶음: 기준 설계·문서·화면·코드 revision과 선택한 맥락.
6. 최신 사용자 요청과 확정된 질문의 답.

참고 자료와 실행 지시를 구분한다. 필요한 참조를 읽지 못하거나 문맥 한도를 넘으면 누락·요약 대상을 드러내고 중요한 수용 조건을 조용히 버리지 않는다. 다음 단계는 원본 산출물과 버전을 받아 이어가며 앞 단계의 장황한 대화 전체가 항상 필수 입력인 것은 아니다.

프롬프트 편집 결과와 채택된 변경에는 이력이 남는다. 이미 시작한 실행은 자신이 사용한 지시·설정 snapshot을 유지한다. 사용자는 실행 준비 또는 작업 상세에서 앱이 조립해 전달할/전달한 지시문을 확인한다. 제공자 내부의 공개되지 않은 지시까지 보여 준다고 약속하지 않는다.

## 여러 AI의 네 가지 운영 방식

| 방식 | 역할과 실행 | 결과 처리 |
| --- | --- | --- |
| 단일 AI | 한 역할이 한 작업 수행 | 결과 하나 검토 |
| 분업 | 대표가 다른 작업을 배정. Windows·Android·공통 계약처럼 책임 분리 | 의존성에 따라 검토 후 로컬 통합 |
| 후보 비교 | 동일 입력·기준·수용 조건으로 여러 후보 실행 | 사용자 채택 후 반영. 완료 속도만으로 자동 채택하지 않음 |
| 독립 검토 | 작성자와 별도 세션이 결과 revision 검토 | 문제를 원래 작업에 돌려보내고 새 결과 재검토 |

단계별 검토/자율 실행은 **진행 정책**, 위 네 가지는 **팀 운영 방식**이다. 둘을 같은 옵션으로 합치지 않는다. 사용자 설계 확정과 명시적 실행 시작은 별도다.

대표 1명 + 작업자 최대 3명이 기본 팀 형태다. 검토자·통합자도 역할만 다를 뿐 같은 슬롯을 사용한다. 여러 팀이나 후보 비교가 있어도 기존 호스트 cap을 공유한다. 슬롯 부족은 대기열이며 새 팀마다 상한이 리셋되지 않는다. 호스트 제약의 정확한 경계는 [설계 구조](ARCHITECTURE.md)를 따른다.

## 분리, 통신, 실패

기획 후보는 별도 초안 namespace를 사용한다. 코드 구현은 같은 기준 commit에서 생성한 전용 worktree를 사용하며, 공유 계약 변경은 담당 한 명 또는 선행 작업으로 직렬화한다. Worktree만으로 시스템 접근 권한이 제한되는 것은 아니므로 실행 권한은 호스트가 따로 검증한다.

작업 메시지는 진행·질문·장애·완료로 구분하고 run/task/attempt와 발신자·수신자·순서를 기록한다. 사용자는 작업자에게 직접 말할 수 있고, 업무 범위를 바꾸는 지시는 대표의 작업 계획에도 반영된다. 같은 질문을 여러 화면에서 답해도 한 번만 적용된다.

- worker의 완료 보고 → 호스트 검증 → 검토 대기 → 수용 → 통합은 별도 상태다.
- 재시도는 새 attempt다. 이전 attempt의 늦은 완료·heartbeat가 새 결과를 완료 처리할 수 없다.
- 일시정지는 새 배정을 멈춘다. 중단 요청·중단 확인·결과 미확인을 구분한다.
- 재연결·재시작 시 실제 실행과 미확인 요청을 먼저 대조한다. 상태를 모른다는 이유로 같은 작업을 바로 재실행하지 않는다.
- 질문이 해소되면 관련 대기 작업만 재개한다. 실패한 후보가 있어도 다른 후보와 기존 결과는 유지한다.
- 일반 CLI 지원과 구조화된 관리형 작업자 지원을 구분한다. 구조화 제어가 없는 제공자를 제어 가능으로 표시하지 않는다.
- provider-native 자식은 제공자가 소유하는 상태를 표시한다. 지원되지 않는 개별 중단·모델 변경·직접 메시지 버튼을 만들지 않는다.
- 채택하지 않은 후보는 기록과 함께 보관한다. 작업 사본·미반영 변경 삭제는 별도 명시적 동작이다.

## 기획 단계의 권한

기획 프로필의 “코드를 실행하지 말라”는 문장만으로 제한을 구현하지 않는다. 호스트가 허용한 기획 namespace 도구만 제공하고 제품 소스 write·일반 셸·코드 실행을 차단한다. 해당 제한을 보장하지 못하는 adapter는 제한된 기획 편집에 사용 가능하다고 표시하지 않는다.

기획 후보 생성과 AI 검토는 문서·scene을 다룬다. 설계 확정은 사용자 판단이며 그 순간 구현 작업자를 시작하지 않는다. 빠른 수정은 전체 PRD 대신 목적·대상·완료 조건을 가진 TaskDefinition과 별도 실행 시작을 사용한다.

## 기존 화면에 배치하는 방식

새 제품 최상위 메뉴를 추가하지 않는다. 검토 패키지의 “AI 운영 설계”는 이 보강안을 읽는 문서 탭이다.

| 화면 | 배치 계약 |
| --- | --- |
| D36 AI 설정 | 연결 AI / 역할 프로필 / 팀 프리셋을 같은 본문에서 전환. 프롬프트·기본 모델·도구·권한·버전 편집 |

| D15 실행 준비 | 팀 운영 방식, 진행 정책, 역할별 provider/model/effort, 적용 지시 미리보기, 준비 상태 확인 |

| D19 후보 비교 | 같은 기준 버전, 후보별 AI 설정·산출물·검증·차이·관측 사용량. 채택과 통합 분리 |
| D20/D27 검토·받은 요청 | 독립 검토 결과와 답변 대기 질문을 기존 화면에 연결 |
| M04/M07/M08/M15 | 적용 역할·모델 확인, 작업자 선택, 질문 응답·검토, PC가 허용하는 다음 실행 설정. 설치·인증은 PC 설정으로 안내 |

좁은 화면은 역할 설정을 한 열의 상세 sheet로 연다. 두 번째 목록 열을 만들지 않는다. 모델을 변경하면 지원 옵션을 다시 검증하고, 선택이 사라진 값은 오류·복구 안내와 함께 보존한다. 지원하지 않는 제어는 이유를 표시한다. 키보드 label·focus 복귀·Android Back 순서를 기존 계약에 맞춘다.

## 구현 인계와 완료 조건

- G1/W01: AgentProfile, TeamPreset, 설정 snapshot, ExecutionAttempt, 메시지·질문 계약.
- G3/W04: 기획 역할 적용, 프롬프트 조립, 참조·초안 제한·이력.
- G5/W06: 역할별 모델 binding, 운영 방식, 배정·상태·질문·재시도·복구. provider 설치 자체는 기존 경로 재사용.
- G6/W07: 후보의 동일 기준 비교, 독립 검토, 정확한 revision의 채택·통합.
- W08: provider 설치·capability와 기존 설정 진입의 연결. W06의 프로필 편집과 책임을 분리.

승인된 설계의 구현 검토에서 다음을 확인한다.

1. 기획·설계·구현·검토별 지시문, 참조, 모델·도구·권한이 실제 작업 예시와 맞는가.
2. AI 없는 단계와 기존 실행을 보는 단계를 구분하는가.
3. 단일·분업·후보 비교·독립 검토의 입력·결과·대기·실패 경로가 보이는가.
4. D15/D17/D19/D36 및 Android 대응 화면에 설정·지원 불가·복구 표현을 반영했는가.
5. 미지원 모델·실행 중 설정 변경·재시작·늦은 완료·후보 일부 실패를 검증할 조건이 있는가.
6. 기획 권한 제한은 호스트가 강제하며, 설계 확정과 실행 시작을 분리하는가.

4번의 화면 보강은 r3 검토 시안에 반영했다. 화면 체험은 예시 상태 변경이며 실제 provider 연결·모델 평가·팀 실행은 제품 구현 이후 검증한다. 전체 설계 승인은 r6 기록으로 보존한다. [단계별 인계·검증·복구](DELIVERY-DESIGN.md)를 함께 따른다.

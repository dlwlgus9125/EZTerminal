# ux2 기준선: 크롬 점유와 주요 여정 (2026-10-23)

개편 전 현재 제품(main `f958e5a`)을 잰 값이다. 새 셸과 흐름은 이 값과 나란히 비교한다.
측정 도구와 원본 결과는 아래에 적었고, 원본 캡처는 실제 프로필 내용이 보이므로 저장소에 넣지 않고
로컬 `artifacts/`에만 둔다.

## 1. 측정 방법

- **데스크톱(실측):** `node scripts/capture-ux-overhaul.mjs g1-baseline --measure`
  - 실제 프로필의 격리 사본(provider 실행 차단, 실제 저장소 HEAD·ref·worktree 불변 확인:
    provider 프로세스 0, 변경 저장소 0)에서 사용자가 열어 둔 실제 대화 탭을 잰다.
  - `scripts/chrome-bands.mjs`가 보이는 `.chat-transcript` 위·아래에 쌓인 가로 띠(헤더, 워크벤치 바,
    도크 탭, 대화 헤더, 하위 에이전트 줄, 입력창, 상태 표시줄)를 찾는다.
  - 두 외형: 사용자 외형(Matrix, CRT, CLI 스킨, UI 130%)과 제품 기본(Dark, 효과 없음, 말풍선, UI 100%).
    Windows 배율 125%(devicePixelRatio 1.25)에서 창 크기 1600×1000, 1280×800, 1024×720.
- **Android(실측):** `pnpm --dir mobile e2e:conversation-journey` (API 29 WebView 74 / API 35) 첫 전송 직후,
  `mobile/e2e/chrome-probe.ts`가 같은 띠를 WebView 안에서 잰다. 결정적 Codex fixture, 393dp 폭.
- **여정 단계 수(정적 산정):** 진입점 인벤토리([`entry-points.md`](entry-points.md))의 코드 경로에서 센
  현재 최단 경로다. 선택·화면 이동·확정·전송을 각 1단계로 세고 입력·읽기·대기는 세지 않는다.
  실측이 아니며, 관문 ①의 셸 골격 여정 스토리가 같은 규칙으로 목표 경로를 센다.

에이전트 줄, 입력창, 상태 표시줄)이 쌓인다.

## 4. 주요 여정: 현재 최단 경로(정적 산정)

전제: 프로젝트가 등록되어 있고 사이드바는 닫혀 있다. 괄호는 근거 행([`entry-points.md`](entry-points.md)).

**어디서 시작해도 같은 화면·같은 후속 흐름**과 크롬 축소다.

## 5. 기준선에서 정할 성공 신호 후보

관문 ①에서 사용자와 확정한다([`success-signals.md`](success-signals.md)).

- 데스크톱 대화 위 크롬: 4줄 → **최대 3줄**, 1280×800·UI 130%에서 본문 비율 33.6% → 목표치 확정 필요.
- Android 채팅 위 크롬: 43% → 목표치 확정 필요(후보: 위 크롬 1줄, 화면의 10% 안팎).
- 새 대화: 생성 화면 3종 → 1종, 라벨 6종 이상 → 1종.
- 받은 요청 수: 공식 3종 → 1종(데스크톱·Android 같은 수).
- J2 캔버스→첫 승인 8단계, 실행 화면 2개 → 1개.

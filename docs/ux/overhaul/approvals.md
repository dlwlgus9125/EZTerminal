## 2026-10-27 · I3 터미널 요청 확정

사용자 "i3 진행하자" → deep-interview로 정리한 요청을 사용자가 확인했다("확인하고 계획 계속"). 실물(b180f95)의 터미널은 명령을

| 질문 | 답 |
|---|---|

| 보낼 대화를 어떻게 정하나 | **같은 프로젝트 마지막 대화 + 바꾸기 메뉴**: 이 터미널 프로젝트에서 마지막으로 본 대화 → 프로젝트 없는 터미널은 전체에서 마지막으로 본 대화 → 없으면 이 프로젝트 새 대화, "보낼 곳: 이름"을 누르면 바꾸기 메뉴 |

**구현 중 정한 것(2026-10-31, 실물·답에 없던 판단)**

- **Git 저장소가 아닌 폴더의 모두 시작**: 위 기본값대로면 저장소가 아닌 폴더에서 모든 작업이 실패하고, 사람이 하나씩 `이 폴더`로 바꿔야 했다. git이 저장소가 아니라고 답한 프로젝트 폴더에서는 기본이
  이 폴더이고 새 워크트리 선택지가 없으며, 폰과 같은 공유 폴더 문장(`함께 시작하면 같은 폴더를 씁니다`)을 보인다. 폰 문장의 끝(`새 워크트리는 데스크톱에서…`)은 데스크톱에서 거짓이라 뺐다. 상태 읽기 실패나
  시간 초과는 저장소가 아니라는 답이 아니므로 선택지를 둔다(큰 저장소에서 선택지가 사라지지 않게). 같은 판단이 시작 창에도 적용되어 `맡기기`도 그런 폴더에서 `새 워크트리…`를 보이지 않고, 워크트리 권장 작업은
  한 번에 시작한다. 왜 선택지가 없는지는 따로 말하지 않는다.
- **받지 않은 제안의 이유**: 실검증에서 빨간 `도구 실패`였던 행을 `제안 받지 않음`으로 바꾼 뒤에도 이유 자리에 host가 AI에게 쓴 영어 문장("Stop suggesting; …")이 보였다. host가 그 문장 옆에 고정 코드(`cap`, `off`, `stopped`,
  `unattended`)를 보내고 앱이 코드로 짧은 이유를 쓴다. 코드가 없거나 모르면 일반 문구이고, 행은 계속 보인다. 턴이 이미 끝난 호출처럼 네 경우 밖의 거절은 일반 문구를 쓴다.
- **표시 시간 문구**: 설정의 제안 시간은 실측 범위 대신 Claude `턴이 끝나고 몇 초 뒤`(실앱 0.9–2.8초, 실험 2.6–7.9초), Codex `턴이 끝나고 10초쯤 뒤`(실앱 10.0–13.2초, 실험 6.6–15초)로 쓴다.
- **계획 모드로 끝난 턴**: 입력창이 제안을 숨기므로 Codex 예측 분기를 돌리지 않는다.
- **영문 단어가 없는 제목의 브랜치**: `suggest/task-<작업 id 앞 8자>`. 순번을 쓰면 다음 배치와 충돌했다.

### 장시간 연속성 구현 중 정한 것 (조정 작업자의 위임 판단, 사용자의 결정이 아니다)

아래는 모두 시안 결정과 같은 위임("단순승인 말고 시안 제대로나오면 남은 단계까지 모두 진행")으로 조정 작업자가 정했다. 사용자가 화면이나 글을 보고 고른 것이 아니므로 사용자가 보고 바꿀 수 있다. 근거는
[구현 기록](../reviews/2026-11-01-long-run-implementation.md)에 있다.

- **재개 줄은 AI별이다.** 한도는 AI마다 따로 풀리므로 줄도 AI마다 하나이고 `대화 N개가 차례로`는 그 AI의 대화만 센다. 계획의 "AI를 가리지 않는 한 줄"을 대체한다.
- **Codex 트레이 글.** 시안의 `지금 도구가 끝나면`은 Codex에서 거짓이다. 도구가 도는 중에 약 0.9초 만에 들어갔다(실제 2회, 893ms·944ms). 그래서 도구 옆 Codex는 `곧 들어갑니다 · 도구를 기다리지 않고 이 턴에`다. Claude는 시안 그대로다.
- **`실행 중에 끼워넣음` 표시는 들어갔다는 뜻이지 따랐다는 뜻이 아니다.** 앱이 아는 것은 도착뿐이다. 실제 실행에서 Haiku가 끼워넣은 지시를 한 번 따르지 않았고(같은 지시를 평범한 말로 다시 쓰자 3/3 따름), 표시는 그대로 두되 따랐다고 말하지 않는다.
- **자동 이어가기는 사람의 메시지 없이 연달아 3번까지다.** 네 번째 멈춤은 `ask-reset`으로 먼저 묻는다. 멈춤 하나가 한 번이고(재시도는 세지 않는다), 사람의 메시지가 세기를 지운다. 시안에 없던 상한이다: 도는 대로 한도에 다시 걸리는 작업이 사람 없이 끝없이 돌지 않게 한다.
- **관리 자식은 수동 `이어서 하기`를 받는다.** 자동 재개는 없다. 두 AI 모두 실제 CLI를 스텁에 붙인 `*-limit-child`로 경로를 확인한 뒤 켰다(`MANAGED_RESUME_PROVEN`). 실제 한도에서 본 것은 아니다.
- **붙잡힌 대기열이 있으면 시각이 되었을 때 "Continue." 대신 대기열을 푼다.** 거절된 프롬프트는 세션에 남아 있어, 다음 턴이 그것을 함께 읽는다. 단계는 `cancelled`다.
- **잠자기는 "앱이 닫혀 있음"이 아니다.** 예약은 그대로이고, 깨어나면 네트워크를 기다려 첫 전송을 60초 늦춘다. D5의 "다시 열 때 묻기"는 앱이 실제로 닫혀 있던 경우만이다. 잠자기와 깨어나기는 돌려 보지 않았다.
- **자동 재개된 턴은 사람이 보낸 턴으로 친다.** 그렇지 않으면 이어서 한 일에 요약이 없다.
- **`그대로 두기`와 `직접 보낸 메시지도 거절됨`의 머리글과 목록은 `한도로 멈춤`이다(시안대로).** 계획 8단계의 "목록에는 아무것도 없다"를 뒤집는다. 대화에 다른 턴이 돌면 그 턴의 상태로 돌아가고, 카드의 `이어서 하기`는 남는다. `요금제에 없음`도 같은 글이지만 버튼이 없어 다른 턴이 돌면 닫힌다.
- 시안 승인 뒤 생긴 글이다. 조정 작업자가 쓴 그대로 들어갔고 **사용자가 본 적이 없다**: `지금 시도를 눌러 "Continue."를 보내는 중입니다.`, `이어서 하기를 눌러 "Continue."를 보내는 중입니다.`, `"Continue."를 보내는 중입니다.`, `자동으로 3번 연달아 이어서 했습니다. 이번에는 먼저 묻습니다.`, `도구를 기다리지 않고 이 턴에`, `한도로 멈춘 대화라 새 메시지로 보냅니다. 예약된 자동 재개는 취소되고, 해제 전이면 거절되어 대화에 남을 수 있습니다.`, `누르기 전에 이 카드의 상태가 바뀌었습니다. 지금 상태를 확인해 주세요.`, `앱이 응답하지 않았습니다. 카드를 확인한 뒤 다시 눌러 주세요.`, `누르기 전에 이 메시지의 상태가 바뀌었습니다. 지금 상태를 확인해 주세요.`, `먼저 묻습니다`

시안과 실캡처의 차이:

- 실캡처의 AI는 모두 가짜 Codex다(데스크톱 모델 이름 `GPT 5.6`, 폰은 fixture 그대로라 `GPT 5.…`로 잘림). 시안은 `steer-tray`·`steer-phone-tray`만 Codex이고 나머지는 Claude(Opus 5.5)다. **Claude의 트레이 글은 어느 캡처에도 없고** 한도 카드의 `Claude · 5시간 한도`도 story에만 있다. 실제 CLI로 본 Claude 화면은 `artifacts/long-run/live/`(로컬)에 있다.
- 시안의 도구 행(`파일 1개 읽음`, `$ pnpm test`)이 실캡처에는 없다. 가짜 Codex는 도구를 부르지 않아, `steer-tray`의 `도구를 기다리지 않고`가 가리키는 도구가 화면에 없고 `N초째 작업 중`만 있다. 시안의 앞선 글(`18분 뒤 한도로 멈춤`)도 실캡처는 `0초 뒤`다: 가짜 Codex가 턴을 곧바로 거절한다.
- 대화 제목이 다르다. 시안은 `장바구니 테스트 고치기`이고 실앱은 첫 메시지라 머리글이 말줄임으로 끝난다. 한 대화의 턴을 이어 간 것이라 끼워넣은 메시지와 앞선 카드가 뒤 캡처의 위쪽에 보인다.
- 시각은 찍은 때의 것이다. `limit-waiting`은 22:49 해제 예정·22:51 시도(시안 15:10·15:12), `limit-ask`는 11월 4일(시안 11월 3일). 목록은 재개가 자정을 넘겨 `한도 대기 · 11월 2일 (월) 00:53`처럼 날짜가 붙는다(시안 `15:12`). 날짜가 붙는 것은 제품 규칙이다.
- `limit-waiting`은 Codex의 5시간 한도다. 측정한 계정의 Codex 창은 10,080분 하나뿐이라, 그런 계정에서는 이 화면이 나오지 않고 늘 먼저 묻는다. 시안은 Claude의 5시간 한도다.
- `limit-resumed`의 앞선 턴은 시안의 18분이 아니라 `0초 동안 작업함`이고, 머리글은 시안처럼 `준비됨`이다.
- `steer-behind-approval`의 도크는 실제 도크라 `위치`·`이유` 줄과 `이 대화 동안 허용`이 더 있다. 왼쪽에 승인 항목이 있고 위 막대에 `기다리는 것 1`이 있다. 시안 story는 대화 패널만이다. `long-run-list`와 다른 데스크톱 캡처도 전체 창이다.
- `long-run-list`는 모두 Codex다(시안은 두 AI). 순서는 시안의 순서가 아니라 최근 갱신순이고, 줄에서 둘째 대화가 60초 뒤를 보인다. 시안에 없는 터미널 행이 있고, 찍는 순간 대화 패널은 마지막 대화다.
- `long-run-settings`는 `wrap-up-settings`처럼 설정 사이드바를 440px로 넓혀 찍었다. 그 뒤의 대화는 시안의 한도 대화가 아니라 끝난 대화다.
- 폰 캡처의 입력창 위 `기기에 저장 중...`은 장시간 연속성과 무관한 기존 폰 안내다. 에뮬레이터 시계는 UTC라 상태 표시줄과 앱 시각이 시안과 다르다.
- `limit-phone-card`에서는 사용량 막대 셋이 입력창의 자기 줄로 내려가 입력창이 시안보다 한 줄 높다. 시안은 `승인 후 실행` 옆에 있다. 실기기의 글자 폭 때문으로 보이고 고치지 않았다.

- **프롬프트 주입**: 맡은 일과 무관한 주입은 네 모델 모두 따르지 않았다(0/38). **사람의 작업이 그쪽으로 이어지면 강한 모델은 페이지 지시를 따라 간다**: Opus와 `gpt-6.1-sol`이 가짜 `evil.example`로 이동을 시도했고(4/4) 호스트의 거절만이 막았다. 그 뒤 페이지가
  제시한 `curl` 셸 시도는 0/4였고 둘 다 막혔다고 보고했다. 안내문을 붙여도 측정되는 차이가 없어 표시만으로는 막을 수 없다 → **사이트 허용은 모델이 아니라 호스트가 모든 이동·리다이렉트·새 창에서 강제한다.**
- **승인**: 두 AI 모두 브라우저 도구를 막아 주는 프로바이더 층이 없다. 호스트의 도구 처리기가 유일한 관문이다. Codex 전체 권한은 `approvalPolicy:'never'`라 조작 도구에 `approval_mode:'approve'`가 필요하고, 그러면 계획 모드에서도 돈다 → 호스트가 계획 모드를 직접 막는다.
- **Electron**: 작업 폴더 안 `file:` 페이지가 폴더 밖 파일을 읽었고 `webRequest`만 막았다.
- 재지 못한 것: 실제 외부 사이트, 여러 턴에 걸친 설득, 전체 권한에서의 주입, DevTools와 `debugger` 동시 사용, 이 PC 밖의 숨겨진 창 렌더링.
- 시안 단계로 넘김: 16화면(D1–D16). 폰은 결과 행만이라 외부 조작 승인은 데스크톱을 기다린다(D16).

  여정 종료 지점 통일, 승인 화면 가드 강화와 1.0 화면 은퇴, 1부·2부 충돌 해소(대체 예정 표시, 파일 탭 편집 제거),
  미흡수 규칙 복원, 결정 질문 보완(D①-7·9·10·11), 비교 조건 통제, 실제 SidebarShell 사용, 검토 도구 실패 검출,
  fixture 시각 합성화, CSS 토큰. 관문 ②로 넘긴 것: Android 한 줄 헤더의 ⋯ 메뉴에 작업 위치·확장·heartbeat 연결,
  탭 줄 키보드 이동(Dockview 탭 헤더로 대체).
- 2차 확인(어드바이저 + Codex gpt-6-astra max, 판정 "수정 후 진행"): 1차 13건 중 7건 해결·6건 부분 해결. 반영:
  여정이 끝 상태를 단언한 뒤에만 완료(새 대화는 가짜 호스트가 생성·전송을 받아 대화가 열림, 승인은 응답됨 상태,
  결과는 파일 변경 표시, 캔버스는 production React Flow 캔버스에 단계 표시, 단계 수가 다르면 실패), 승인 화면
  가드를 실행되는 `designReferenceCases` case와 축(두 언어 axe·screenshot·초점·viewport·넘침), 실제 날짜, 답이
  채워진 기록 행에 묶음, 검토 수집기가 모든 캡처에서 페이지 오류·크기를 검사, 수치 설명 정정(본문 증가를 띠 높이와

  단계 수를 하나로 고정(B 이어가기 2단계는 목록에서 대상이 바로 보일 때만, A 워크트리 4단계는 로컬 묶음이 접혀 있을
  때만, 둘 다 단언), 결과 여정은 이름 있는 파일의 변경 화면이 보여야 완료, 승인 화면 가드는 건너뛴 테스트
  (`test.skip`·`describe.skip`·본문 안 skip)·다른 story·다른 screenshot·같은 언어 두 번·case와 무관한 다른 언어·
  viewport 밖 넘침 검사를 거부하고 승인 행은 id가 정확히 같은 칸만 인정. 검토 시트의 본문 증가 분해는 반올림 차를
  여백 쪽에 넣어 합이 맞게 했다.
- 4·5차 확인(Codex gpt-6-astra max, 범위: 앞 차수 필수 항목만): 여정 묶음은 4차에서 해결 확인. 승인 가드는 정적 검사를
  하나씩 막으면 다른 우회가 나와서 설계를 바꿨다: visual spec은 고정된 한 문장으로 case를 helper에 넘기기만 하고, 모든
  검증은 manifest `approvedChecker`가 SHA-256으로 고정한 helper 하나가 하며, 답은 표의 `답` 열에서 읽는다. 5차가 고정
  파일을 건드리지 않는 우회 둘(spec 안 같은 이름 helper, 반복 전 case 목록 비우기)을 재현해, helper는 고정 파일에서
  이름 그대로 import해 한 번만 쓰고 case 목록은 맨 위 const 하나를 반복문만 읽게 막았다(테스트 48개). **알려진 한계:**
  가드는 소스 모양을 보는 정적 검사라 모든 실행 경로를 증명하지 못한다. 고정 helper를 바꾸면 해시가 깨져 검토에 드러나고,
  실제 실행 증거는 CI의 `pnpm test:visual`이다. 이 기준으로 관문 ①의 가드 검수를 마친다(추가 차수 없음).

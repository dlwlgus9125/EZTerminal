# EZTerminal 2.0 소프로젝트·일반 대화·실행 흐름 개선 계획

상태: **시나리오 점검을 반영한 수정 후보 · 제품 미구현 · 디자인 미확정**  
검토일: 2026-10-13

최신 시안: **[r4 열기](reference/v2-agent-chat-r4/index.html)** ·
[Android](reference/v2-agent-chat-r4/index.html?device=mobile) ·
[범위와 검증](reference/v2-agent-chat-r4/VISUAL-REVIEW.md).
프로젝트 아래 소프로젝트와 일반 대화를 같은 깊이에 두고, 프리셋·대화로 생성한 흐름을
그래프·목록에서 편집하며 각 단계의 대화로 이어간다. 분기·병렬·승인 대기는 예시 실행으로 체험한다.
P1의 검토 후보이며 제품 구현 완료나 디자인 버전 승인은 아니다. r1–r3 원본은 보존한다.

이번 수정은 첫 메시지 전 기능 탐색을 유지하며, 사용자가 정한 **소프로젝트 = 이전 논의의 기획 단위**,
실행 가능한 그래프, AI의 초안 직접 편집, 일반 대화의 동등한 진입을 반영한다. 기획과 소프로젝트를
별도 부모·자식으로 중첩하지 않는다. 기획은 소프로젝트 안의 선택 가능한 단계 이름이기도 하다.
아래 S01–S30 및 기존 데이터 경계의 ‘기획 단위/planId’는 같은 소프로젝트를 뜻하며,
문서·요구사항을 정리하는 ‘기획 단계’와 구별한다. 승인된 r6와 기존 제품 검증 기록은 소급 변경하지 않는다.

일관되게 만드는 것이다. 첫 메시지 전 스킬 탐색은 여러 기획을 위한 데이터 이전에 의존시키지 않는다.

## 2. 유지할 기준과 설계 범위

- `design_context.required`: true. 시각 기준은 [DESIGN.md](../../DESIGN.md), 활성 UX 계약은
  [frontend-design.md](frontend-design.md), 이 문서는 그 계약에 대한 미승인 보완 계획이다.
- 구현 대응은 `src/renderer/`와 `mobile/src/`. 정확한 값은 기존
  [theme](../../src/renderer/themes.ts)와 [token](../../src/renderer/styles/ui-tokens.css)이 소유한다.
  새로운 브랜드·색상표·자산·DESIGN 프로필 이전은 필요하지 않다.
- r6의 프로젝트·작업공간·Android 전역 탐색을 유지한다. 기존 프로젝트 영역은 집계·도구 진입점으로
  남고, 소프로젝트의 단계 이동은 편집 가능한 그래프·목록이 맡는다. 프로젝트 탭을 고정 실행 단계로
  취급하지 않는다. 단계별 별도 채팅 저장소나 별도 provider 실행 관리자를 만들지 않는다.
- 일반 대화는 기존 프로젝트·작업공간에서 직접 시작한다. 프로젝트 없는 독립 대화는 이번 범위에 추가하지 않는다.
- r1의 native 설정 공유·확장 관리와 r2의 참조·복귀·문서 제안 명시 적용은 유지한다.
  사용자가 선택한 예외는 **AI의 흐름 초안 직접 수정**이다. 그래프 수정에 매번 적용 승인을 요구하지
  않고 변경 내역·되돌리기를 제공한다. 파일 쓰기·도구 권한·실행 시작·노드 승인까지 확장하지 않는다.
  [지원 조사](reference/v2-agent-chat-r1/SUPPORT.md)는 조사 시점의 근거다. 실제 지원은 설치된 provider로 검증한다.
- 고정 desktop handoff, r6 승인본, r1–r3 패키지와 기존 검증 기록을 보존한다.

## 3. 사용자가 보는 구조

프로젝트 바로 아래에 **소프로젝트와 일반 대화가 같은 깊이**로 존재한다. 소프로젝트는 목표가 있는
작업 묶음이며 ‘로그인 개선’과 ‘결제 추가’를 각각 만들 수 있다. 일반 대화에는 소프로젝트·기획·단계
생성을 요구하지 않는다. 필요할 때만 대화를 새 소프로젝트 또는 기존 소프로젝트의 단계에 연결한다.
소프로젝트 내부는 **흐름 → 단계 → 여러 대화·문서·산출물**이며, 흐름은 실제 실행의 순서·분기·병렬·
승인을 제어한다. 단계 종류와 수는 고정 마법사가 아니며 프리셋 이후에도 사용자와 AI가 편집한다.

| 범위 | 소유하는 내용 | 사용자에게 보이는 방식 |
| --- | --- | --- |
| 프로젝트 | 코드·작업공간, 공통 설정, 소프로젝트와 일반 대화 | 하나의 목록에 유형을 구분해 같은 깊이로 표시. 전체/유형/보관 필터 |
| 소프로젝트 | 목표, 흐름 초안·버전·프리셋 출처, 단계, 확정본과 변경 이력 | 목록 → 흐름 그래프 또는 동등한 단계 목록 |
| 단계 | 안정적인 nodeId, 담당 AI·지시·입출력 참조·완료 조건, 문서·여러 대화 | 노드/목록 선택 → 문서·대화 이어가기·새 단계 대화 |
| 일반 대화 | 프로젝트·작업공간과 session/turn/message, 입력·첨부·승인·대기열 | 소프로젝트와 동등한 프로젝트 항목. 계획 없이 사용 가능 |
| 단계 대화 | 같은 세션의 단계 참조와 턴별 사용 버전 | r3 공통 채팅, 소속·참조·원래 단계로 복귀 |
| 실행·결과 | 고정한 graph/baseline 버전, attempt, 실제 담당 세션, 결과·검토 근거 | 편집 초안과 구분한 실행 보기. 기존 실행·검토 서비스 재사용 |

### 탐색과 시작

- 프로젝트 목록·빈 상태에 `새 소프로젝트`와 `새 대화`를 나란히 제공한다. 첫 번째와 두 번째
  소프로젝트 생성 경로는 같다. 기존 빠른 작업은 작업 영역에서 유지하며 일반 대화에 기획을 강제하지 않는다.
- 생성 화면은 이름·목표와 `프리셋 선택 / 대화로 구성`을 제공한다. 기능 개발·문제 수정·조사·병렬 구현·
  직접 구성은 시작용 템플릿이며 필수 단계가 아니다. 프리셋 선택은 모델 턴을 발생시키지 않는다.
- 대화로 만들 때는 생성 전 임시 초안에 흐름을 미리 보여 준다. 자연어 요청의 전송은 명시적이며
  불명확한 요청은 질의하고 구조를 임의로 바꾸지 않는다. 생성 전 취소는 빈 소프로젝트를 남기지 않는다.
- 생성 뒤에도 같은 그래프를 직접 또는 AI 대화로 편집한다. 단계 이름·종류·담당 AI·지시·연결을 변경하며
  조건 분기·병렬 시작·합류·승인 대기를 구성한다. 실행 시작과 그래프 편집은 별개의 동작이다.
- Desktop은 기존 한 칸 sidebar에서 소프로젝트와 일반 대화를 같은 깊이에 표시한다. 소프로젝트 내부의
  그래프/목록과 단계 상세는 본문에서 전환한다. 별도의 기획 부모 계층이나 두 번째 sidebar를 만들지 않는다.
- Android는 프로젝트의 동등한 항목 목록 → 흐름 목록/그래프 → 단계 상세·대화로 이동한다. 좁은 화면의
  기본은 단계 목록이며 같은 연결 편집 기능을 제공한다. 그래프의 drag만으로 작업 완료를 제한하지 않는다.
- 프로젝트·파일·터미널의 범위는 유지한다. `새 대화`는 항상 일반 대화, `새 단계 대화`는 선택한 단계에
  연결한 대화다. 소프로젝트를 선택했다고 일반 대화가 몰래 소속되지 않는다.
- 전환 시 문서 편집·세션 입력·커서·스크롤·첨부·열린 산출물을 보존한다. 다른 창과 기기의 선택은 독립적이다.
- Android는 목록 → 내용 → 보조 sheet 순서를 따른다. Back은 열린 overlay/키보드 등 기존 입력
  계층을 먼저 처리한 뒤 진입 경로로 돌아간다. 승인 알림으로 들어온 경우에도 이전에 보던 B의 초안과
  위치를 복구하며, `관련 기획 보기`는 승인 대상 A의 실제 항목으로 이동한다.

### 대화에서 시작하고 이어가기

- 일반 대화의 `소프로젝트에 연결`에서 새 소프로젝트 또는 기존 소프로젝트의 단계를 선택한다. 사용할 메시지·자료·결정 요약을
  검토하고 연결한다. 원래 대화는 보존하며 연결만으로 문서를 쓰거나 전체 이력을 다시 전송하지 않는다.
- 기획에 소속되지 않은 일반 대화는 같은 프로젝트의 기획에 연결해 그대로 이어갈 수 있다.
  이미 다른 기획에 소속된 대화는 읽기 전용 출처로 참조하고, 새 논의가 필요하면 명시적으로 새 대화를 만든다.
  실행·검토 세션의 소속과 역할은 재지정하지 않는다. 다른 프로젝트의 세션을 이동시키지 않는다.
- 각 문서에는 `대화 이어가기`를 우선 제공하고 `새 대화`는 별도로 제공한다. 관련 대화가 여러 개면
  제목·역할·최근 상태를 보고 고른다. 기획마다 또는 단계마다 대화 하나만 허용하는 구조가 아니다.
- 대화 상단에는 현재 프로젝트·기획, 참조 대상/버전, 역할과 원래 항목으로 돌아가기를 표시한다.
  참조를 연결한 사실과 실제 해당 턴에 보낸 참조를 구분한다. 전송 후에는 사용한 버전을 확인할 수 있다.
- 원래 항목의 미저장 편집은 보존한다. 기본 참조는 저장된 버전이며, 최신 편집을 사용하려면
  `저장 후 참조 갱신`을 명시적으로 선택한다. 문서 자동 저장이나 숨은 전송으로 편의를 만들지 않는다.
- 다음 단계에는 저장·반영한 문서와 선택한 결정 요약을 넘긴다. 같은 설명을 다시 쓰지 않게 하되
  이전 단계의 전체 대화를 무조건 복제하지 않는다. UI 없는 변경은 디자인 단계를 건너뛸 수 있다.
- 연결된 일반 대화는 같은 sessionId로 단계의 관련 대화에 표시한다. 프로젝트 집계 대화 목록에서는
  소속을 표시해 찾을 수 있고, ‘기획 없는 일반 대화’ 필터에서는 제외한다. 메시지를 새 세션으로 복제하지 않는다.
- 단계 이름 변경·배치 변경은 nodeId와 기존 대화를 유지한다. 단계 삭제는 활성 초안에서 노드/연결을
  제거하고 기존 문서·대화·실행 기록은 보관한다. 삭제된 단계로의 deep link는 보관 기록으로 복구한다.
- 흐름 전체를 수정하는 대화는 `흐름 편집` 범위를 표시한다. 단계의 일반 논의는 자동으로 그래프 변경
  명령이 되지 않는다. AI 흐름 편집은 사용자가 정한 직접 반영 정책과 변경 기록·되돌리기를 따른다.

### 작업과 완료

- 화면마다 현재 상태에 맞는 다음 행동을 하나 우선 표시한다. 변경안이 있으면 `변경안 검토`,
  실행 조건이 갖춰지면 `실행 준비`, 실행 중이면 `담당 AI 대화`, 결과가 있으면 `결과 검토`다.
  모든 단계를 항상 완료해야 하는 고정 마법사로 만들지 않는다.
- 실행 준비에서 이번에 구현할 작업과 필요한 참조 범위를 검토한다. 선택한 작업의 선행 조건과
  참조가 완결되어야 한다. 같은 기획의 무관한 초안 때문에 작은 실행이 막히지 않도록 실행 범위의
  확정본을 만든다. 이 범위 선택은 현재 전체 draft freeze에 추가할 동작이며 구현 완료 기능이 아니다.
- 기준 확정·역할 확인·실행 준비는 한 검토 화면에서 처리할 수 있다. 마지막 `실행 시작`은 명시적이다.
  같은 내용을 중복 확인시키지 않으며 파일 쓰기 등 실제 실행 요청의 기존 승인은 유지한다.
- 실행 준비는 연결 무결성·도달 가능성·필수 참조·분기 조건·합류·반복 한도를 검증한다. 끊어진 단계,
  조건 없는 순환, 미지원 노드가 있으면 편집은 보존하고 실행만 막는다. 판단이 필요한 오류 위치로 이동한다.
- 시작한 실행은 graph revision·노드 설정·참조·권한을 고정한다. 이후 직접/AI 편집은 다음 실행의 초안만
  바꾼다. 재개는 원래 버전, 새 버전 사용은 새 실행이다. 실행 중 그래프를 몰래 다시 해석하지 않는다.
- 분기는 명시적 검증 결과에 따른다. 병렬 작업은 기존 workspace/환경 lease로 격리하며 합류 정책을 명시한다.
  실패 후 수정 반복은 기존 기본 추가 2회를 사용하고 한도 이후 사용자 판단을 기다린다. 승인 대기·중단·
  재시작·응답 미확정은 기존 실행/receipt 경계에서 처리한다.
- 반려나 실패는 해당 결과와 항목으로 돌아가 수정한다. 기존 결과를 남기고 새 attempt/결과로 검증한다.
  다른 작업까지 처음부터 다시 진행하지 않는다. 독립 검토는 구현자와 별도 세션이다.
- 기획 완료와 보관은 구분한다. 완료는 미해결 작업·변경·검토 상태를 확인한 사용자 결정이며,
  보관은 기본 목록에서 숨기는 동작이다. 활성 실행·대기 승인이 있으면 해결 경로를 제시한다.
  보관은 자료 삭제나 실행 취소가 아니다. 복원 후 기존 기록을 다시 열 수 있다.
- `새 기획`은 빈 기획 생성, `복사해 새 기획`은 선택한 저장본/확정본에서 새 ID로 생성,
  `이 버전에서 수정`은 같은 기획의 현재 초안을 대체하는 동작이다. 마지막 동작은 미저장 내용과
  영향 범위를 먼저 보여 준다. 기존 branch를 새 기획 생성 버튼에 그대로 연결하지 않는다.

## 5. 이전 구현과 조화시키는 데이터·동작 경계

아래는 구현 설계에 반영할 조건이다. 실제 필드와 저장 포맷은 B 단계에서 기존 schema를 확장하며 확정한다.

1. **기획과 revision:** stable planId, 제목·상태, 기획별 작업 초안·확정본 연결을 둔다. 기획 목록의
   revision과 각 기획의 내용 revision을 구분한다. A 변경으로 무관한 B의 저장이 stale이 되지 않게 하되,
   공유 파일 쓰기는 기존 원자적 저장/직렬화로 처리한다. commandId와 권한 검사는 모든 쓰기에 유지한다.
2. **실행 권위:** 기존 실행 원장과 task/attempt/result/session ID를 재사용한다. 빠른 작업은 기획 없이
   존재할 수 있다. 실행 소속은 실제 baseline/run에서 검증하고 화면의 현재 선택을 신뢰하지 않는다.
3. **기존 데이터 이전:** 기존 draft는 ‘기본 기획’으로 매핑한다. 기획 확정본은 기본 기획에, quick-task
   확정본은 기획 없는 빠른 작업에 연결한다. 과거 baseline bytes/hash, receipt, 실행 snapshot과 결과를
   다시 작성하지 않고 외부 소속 매핑으로 연결한다. 과거 일반 대화는 이름으로 임의 분류하지 않는다.
4. **이전의 복구:** 이전 전 백업과 참조 무결성 확인, 중간 실패 복구, 반복 실행의 멱등성을 검증한다.
   미확정 요청이 있으면 먼저 원래 명령의 결과를 대조한다. 활성 실행/쓰기에 안전한 이전을 보장하지
   못하는 프로젝트는 구조 전환을 보류하고 기존 실행을 유지한다. 앱 시작만으로 작업을 중단하지 않는다.
5. **구버전 연결:** capability와 schema 협상을 추가한다. 다중 기획을 모르는 client에는 호환되는
   조회와 업데이트 안내를 제공하며, 다중 기획 변경 명령은 거절한다. 누락된 planId를 현재 선택으로
   채우지 않는다. 새 포맷을 이해하지 못하는 구버전 host가 저장 파일을 덮어쓰지 못하게 한다.
6. **초안과 복귀:** 문서 복구 키는 PC 권한 경계+project+plan, 항목 편집은 entity ID, 대화 초안은
   기존 session ID를 사용한다. 선택·읽던 위치·return target은 기기/창별 보기 상태다. 다른 기기에서
   같은 문서를 열어도 상대 기기의 화면을 강제로 이동시키지 않는다. 문서 저장 실패도 초안 폐기로 이어지지 않는다.
7. **대화 연결:** 기존 세션 저장소에 소속/참조 연결을 추가한다. 대화 원문을 두 번째 저장소에 복제하지
   않는다. 실행·검토는 immutable 연결, 일반 논의는 선택한 참조와 해당 턴의 snapshot을 기록한다.
   돌아갈 항목이 없으면 소속 기획/기록으로 복구하며 대화는 남긴다.
8. **공유 자료:** 기획 소유의 화면·요소·자산은 기본적으로 그 기획에 남긴다. 프로젝트 공통으로 사용할
   자료만 명시적으로 공유한다. 다른 기획의 초안을 실시간 상속시키지 않고 버전이 고정된 참조로 연결한다.
   공통 설정 변경은 새 실행에 적용하며 진행 중 역할/도구 설정 snapshot은 유지한다.
9. **동시 실행:** 기획 간 동일 파일·통합 대상·테스트 환경 충돌은 기존 환경 lease와 통합 정책에서
   조율한다. 기획이 다르다는 이유로 자동 병렬 실행하거나 다른 실행의 자원을 정리하지 않는다.
10. **전체 기록:** 백업/복원·보관·검색·원격 protocol·암호화 초안에도 기획 경계를 포함한다.
    [기록 패키지 검증](../../src/main/project-archive-package.ts)의 hash/참조 검사를 유지한다.
    기획 하나만 내보내는 별도 패키지 기능은 이번 범위에 넣지 않고 기존 프로젝트 전체 백업을 확장한다.

## 6. 첫 메시지 전 탐색과 단계별 권한

원래 문제의 완료 조건은 실제 Codex/Claude 환경에서 첫 메시지 없이 설치된 기능을 확인하는 것이다.
시안에 스킬 이름이 표시되는 것만으로 완료 처리하지 않는다.

- 조회 범위는 실행 PC·사용자/인증 경계·provider 실행 identity·작업 위치·설정 revision·정책을 포함한다.
  기획 선택만으로 provider 설정을 복제하거나 새 실행 폴더를 만들지 않는다.
- 설치된 항목, 현재 scope에서 활성화된 항목, 현재 세션에 적용된 항목을 구분한다. 캐시는 범위와
  마지막 확인 상태를 보여 준다. 설정 변경·외부 변경·프로젝트/PC 변경 시 재검증한다.
- provider 초기화나 로컬 조회가 필요할 수 있지만 기능 탐색을 위한 사용자 메시지·모델 submit은 만들지 않는다.
  취소·시간 제한·호스트 종료 시 조회를 정리한다. 조회 성공을 인증/실제 MCP 호출 성공으로 확대 해석하지 않는다.
- 일반 논의는 실제 capability 안에서 스킬·MCP를 선택한다. 도구 없는 구조화 제안과 관리형 실행/독립 검토는
  해당 서비스의 제한을 따른다. 공통 UI에 미지원 이유와 가능한 다음 동작을 표시한다.
- Codex 논의에서 구조화 제안이 필요하면 직접 편집 또는 지원되는 제안 provider 선택을 안내한다.
  제공자를 자동 변경하거나 일반 대화를 도구 없는 세션으로 몰래 전환하지 않는다.
- 확장 관리 후 현재 대화에 즉시 반영할 수 없는 경우 `새 대화부터 적용`을 표시한다. 기존 대화를 보존하고,
  필요한 경우에만 사용자가 새 대화를 만들어 참조/초안을 검토 후 이어간다. 진행 중 세션을 자동 재시작하지 않는다.

P2의 조회 가능성은 시안 단계에서도 소스/읽기 전용 실험으로 먼저 확인한다. 특정 API가 없으면
지원되는 조회와 상태를 설계에 반영하며, 숨은 첫 메시지를 보내는 대체 경로는 채택하지 않는다.
제품 구현 단계마다 해당 변경의 검사를 수행하며 종합 단계까지 회귀 확인을 미루지 않는다.

### P1에서 끊김 없이 체험할 대표 여정

1. **흐름이 필요한 사람:** 빈 프로젝트 → 새 소프로젝트 → 프리셋 또는 대화로 구성 → 그래프 수정 → 단계 문서/대화 → 실행 준비·명시 시작 → 검토/승인 → 완료.
2. **질문만 하는 사람:** 프로젝트 → 새 일반 대화 → 첫 메시지 전 스킬 확인 → 대화 계속. 소프로젝트를 만들지 않아도 종료·재개 가능.
3. **대화가 작업으로 발전한 사람:** 일반 대화 → 새/기존 소프로젝트의 단계에 연결 → 같은 대화/입력 유지 → 문서·흐름으로 복귀.
4. **여러 일을 진행하는 사람:** A 문서·대화 작성 → B 소프로젝트 또는 일반 대화 → A 실행 승인 알림 → 원래 B 입력 복귀.
5. **작은 수정만 필요한 사람:** 기존 빠른 작업 → 범위/완료 조건 확인 → 준비·시작 → 검토. 소프로젝트 생성을 강제하지 않음.
6. **실행 중 개선하는 사람:** 실행 v1 → AI가 초안 v2 편집 → 실행 v1의 대화·승인·결과 유지 → 다음 실행에서 v2 사용.
7. **조건·병렬을 쓰는 사람:** 화면/API 병렬 → 모두 합류 → 검토 분기 → 실패면 한도 내 수정, 통과면 승인 대기 → 명시 승인 후 완료.

## 8. 검증 계약과 이번 확인 범위

**이번 확인:** 소스·production story·기존 인계·r1/r2 계약을 대조했다. headless Chromium에서
r2의 Windows/Android 각 개요·기획·빈 대화·작업 화면과 문서↔대화 왕복을 점검한 관찰은
[별도 기록](reviews/2026-10-13-agent-workflow.json)에 둔다. 이는 실제 provider나 Android APK 검증이 아니다.
기존 121개 시안 검사와 G1–G8 제품 검사 기록을 이번 계획의 통과 수치로 재사용하지 않는다.

이번 문서 검사에서 `pnpm docs:check`가 통과했고, 새 계획의 상대 링크 누락은 없었다.
S01–S30의 고유 ID와 A/B/C/D 작업 대응을 확인했다. r1의 파일 76개·근거 12개와 r2의 파일
109개·근거 20개는 기존 manifest hash와 모두 일치했다. 브라우저 관찰 중 JavaScript 오류와
외부 요청은 없었으며, 두 화면 크기에서 문서/대화 초안 왕복과 시안의 모델 턴 0을 확인했다.

**향후 검사:**

- 문서: `pnpm docs:check`, 후보 계획의 상대 링크·시나리오/단계 대응 검사. 로컬 `.ezpowers` design
  검사 도구/managed profile은 현재 설치되어 있지 않으며 이번에 도입하지 않는다. 저장소의 소유권 규칙을 따른다.
- 데이터/host: 두 기획의 동시 편집, 잘못된 plan/run/session 조합 거절, immutable hash/receipt 보존,
  실패한 이전 재개, 구버전 연결, 실행 중/미확정 요청, backup 왕복을 검사한다.
- 실제 provider: 첫 전송 전 조회, 설치 scope·외부 변경·현재 세션 반영, 실제 첫 전송의 스킬/참조 전달,
  metadata 조회 시 submit 0회를 관찰한다. 타입 정의나 가짜 provider 성공으로 대체하지 않는다.
- production UI: 기존 PlanningWorkspace/StructuredAgentSession/Execution/Result/MobileV2 stories에
  S01–S30의 관련 상태를 추가한다. `pnpm typecheck`, `pnpm lint`, 관련 단위·host 검사,
  `pnpm test:storybook`, `pnpm test:visual`과 일반 `pnpm e2e`를 적용한다.
- 접근성/시각: 기존 DESIGN/UX 기준과 r6를 나란히 비교한다. Windows 800/1024/1440 이상 폭,
  150% UI scale, 200% text zoom, Android 360/390 폭·키보드·safe area·Back, 한영 긴 이름,
  말풍선/CLI·기존 테마, keyboard focus와 screen reader 읽기 순서를 확인한다.
  비교 없이 snapshot을 갱신하지 않는다.
- Android: web 모의 화면과 APK/실기기 검증을 분리한다. 실제 IME, 오프라인·재연결·프로세스 재시작,
  host 교체와 secure storage 복구가 남으면 그 상태를 그대로 기록한다.
- 성능 벤치마크는 사용자 요청이 없으므로 실행하지 않는다. 이 계획 점검으로 제품 빌드·배포 완료를 주장하지 않는다.

현재 화면 후보와 검사 범위는 [r4 검토 기록](reference/v2-agent-chat-r4/VISUAL-REVIEW.md)을 따른다.
제품 밖 독립 채팅, 별도 로드맵/간트, 소프로젝트 간 초안 자동 동기화와 신규 디자인 시스템은 추가하지 않는다.

## 9. 실행 그래프와 AI 앱 스킬의 구현 계약

- 그래프는 저장소의 Project Map과 별도 실행 도메인이다. 기존 Project Map의 검증/authoring 경험은
  참고하되 architecture diagram 파일을 실행 명령으로 해석하지 않는다. 기존 fixed role enum에 사용자
  단계 이름을 계속 추가하지 않고 `nodeId + operation/role + title`을 분리한다.
- 첫 노드 라이브러리는 AI 작업, 조건 분기, 병렬 시작, 결과 합류, 사용자 승인, 완료를 기준으로 설계한다.
  임의 셸 코드를 그래프 필드에 넣어 바로 실행하는 기능이나 외부 SaaS 트리거는 이번 시안에 포함하지 않는다.
  제품 확장 시에도 실제 도구/명령은 기존 권한 경계로 전달한다.
- 각 노드는 stable ID, operation, 역할/AI 설정, 입력 reference, 지시/완료 조건, 출력 artifact 계약을 가진다.
  edge는 출발/도착 및 명시적 outcome port를 가진다. view 좌표와 실행 의미를 분리한다. 노드를 옮기는 것과
  실행 순서를 바꾸는 것을 혼동하지 않게 한다. 실행 순서는 연결이 소유한다.
- validator는 중복/없는 ID, 시작점, 도달 불가, 종료 없는 경로, 타입이 맞지 않는 입력, 조건 포트 누락,
  무제한 순환, 모호한 합류, 미지원 operation과 실행 권한을 확인한다. 조건은 검증 결과와 명시적 값으로
  평가하며 AI의 자유 문장/화면 위치에서 성공을 추론하지 않는다. 반복 회차별 합류/출력/승인을 격리한다.
- run은 graph fingerprint/revision 및 baseline·node settings·inputs를 고정한다. 기존 task/attempt/lease/
  session/result에 node execution identity를 연결한다. pause/resume은 같은 snapshot을 사용한다.
  취소·실패·사용자 거절·검토 반려와 구현 완료를 구분한다. 배포/통합은 완료 노드 진입만으로 실행하지 않는다.
- 앱 전용 스킬은 절차 안내이며 실제 권위는 host의 검증된 명령 API다. 예정된 명령 범위는 흐름 조회,
  프리셋 생성, 초안 patch, validate, changes/undo, run 조회·명시 start/pause/resume이다.
  이름/프로토콜은 구현 단계에서 확정하며 현재 제공되는 API처럼 문서화하지 않는다.
- UI와 AI 모두 같은 command/revision/validation 경계를 사용한다. project/subproject/node/run IDs,
  host identity, expectedRevision, idempotent commandId를 확인한다. 일반 대화에 대상이 없으면 지정 요청을
  표시하고 최근 선택을 추정해 쓰지 않는다. 이미 진행한 실행/승인·결과를 AI가 덮어쓰지 못하게 한다.
- AI는 초안 편집을 직접 적용할 수 있지만 오류가 있는 초안은 실행할 수 없다. 변경자·대화·command ID와
  전후 revision을 기록한다. undo는 기존 이력을 삭제하지 않는 새로운 보상 revision이다. 다른 창이 쓴
  내용을 덮어쓰지 않도록 충돌 시 최신 변경을 제시하고 재계산한다.
- 먼저 EZTerminal 안의 Codex/Claude에 앱 스킬과 연결된 도구를 노출하는 후보로 설계한다. 외부 데스크톱
  앱/CLI 연결 범위는 아직 확정되지 않았으며 설치·인증·제공자 지원을 별도로 확인해야 한다. 기존 native
  스킬 설정 공유 요구는 유지한다. 스킬이 목록에 있다는 사실과 현재 실행 권한·도구 연결을 구별한다.
- 앱 스킬도 첫 사용자 메시지 전 discovery에 포함한다. 로드 실패/미지원/오프라인은 실제 상태를 표시한다.
  안내문만 주입하고 앱 상태 변경이 된 것처럼 보이는 구현은 완료로 인정하지 않는다.

### 추가 제품 검증

S31–S46에 대해 model/schema → host commands → provider tool binding → desktop/mobile story → 일반
`pnpm e2e` 순서로 검증한다. 병렬 결과 중복·부분 실패·반복 회차 합류, 승인 후 재시작, 상태 미확정 start,
삭제된 노드의 과거 대화, immutable run과 수정 draft의 공존, AI/UI 동시 편집을 포함한다.
첫 메시지 전 스킬 사용과 실제 명령 전달은 설치된 두 provider에서 확인해야 한다. r4 HTML은 이 제품
검증을 대신하지 않으며 성능 벤치마크는 여전히 별도 명시 요청이 있어야 한다.

# 내장 브라우저 구현 기록 (Claude 데스크톱 기능 흡수 4묶음)

상태: 구현과 로컬 검수 완료. 공개 배포나 설치판 확인을 뜻하지 않는다. **실제 외부 사이트는 시험하지 않았다: 모든 페이지는 루프백 스텁이었다.**
계약: [frontend-design §28](../frontend-design.md#28-내장-브라우저), [agent-collaboration "내장 브라우저"](../../design/agent-collaboration.md#내장-브라우저).
결정 기록: [approvals.md "내장 브라우저 검증"](../overhaul/approvals.md#2026-11-02-내장-브라우저-검증claude-데스크톱-기능-흡수-4묶음-실험-결정). 브랜치 `feat/in-app-browser`. 시안·구현 판단은 사용자의 위임으로 조정 작업자가
했다: 사용자가 화면을 보고 승인한 것이 아니다.

## 요청과 범위

사용자 요청(2026-10-29 확정, 2026-11-02 답): dev 서버 미리보기 창, AI가 클릭·입력·스크린샷으로 확인하는 도구, 요소를 골라 입력창에 첨부, 수정 뒤 자동 화면 확인(기본 꺼짐). 데스크톱 전용이고 폰은 결과 행만.
사이트 범위는 "localhost는 자유, 외부는 사이트별 허용", 별도 프로필, 쿠키 가져오기 없음.

- 하지 않은 것: 폰의 브라우저와 폰에서의 승인, 파일 올리기, 쿠키 가져오기, 관리 자식 대화의 도구, 실제 외부 사이트.

## 구현

- **공용**: `src/shared/browser.ts`(사이트 등급, 거절 코드, 권한별 규칙, 승인 요청 모양, `looksSecret`), `src/shared/dev-server-url.ts`, payload 넷(`browser-step`·`browser-shot`·`browser-blocked`·`browser-check`). DB
  스키마는 바꾸지 않았다: AI 도구 스위치는 전부터 있던 `browser_enabled` 열이고 이번에 처음 화면이 생겼다.
- **호스트**: `browser-view-manager.ts`(뷰, 막기, 사람의 이동), `browser-network-guard.ts`(파티션의 모든 요청), `browser-cdp.ts`(debugger로 읽기·입력·스크린샷), `browser-tools.ts`(도구 8개와 유일한 관문),
  `browser-approvals.ts`, `browser-site-store.ts`(봉한 허용 목록), `browser-rows.ts`, `browser-shots.ts`, `browser-dev-urls.ts`, `browser-check-coordinator.ts`, provider 어댑터의 허용 목록과 이미지 행 처리.
- **화면**: `src/renderer/browser/`(패널, 허용 창, 설정), `chat/rows/BrowserRows.tsx`, 결정 도크의 브라우저 카드, 입력창의 요소 첨부. 폰은 같은 행과 기다림 한 줄, 피드는 읽기 전용.
- **곁에서 고친 것**: 도구 결과의 이미지 바이트가 행 `text`에 들어가던 것(`[image]`로, 실패 테스트부터), 모든 승인의 `허용`이 포인터를 올리면 호박색을 잃던 것.

### Android

`mobile/e2e/browser-rows-journey.ts`, 가짜 Codex 격리 데스크톱, 360×800, 한국어, Matrix. 최종 소스의 APK로 API 35와 API 29(WebView 74)에서 통과했다(`artifacts/in-app-browser/android/api35-matrix/`·
`api29-matrix/`(로컬), 점검 7, 그림 7장씩). 제품 코드는 고치지 않았다.

- 허용한 사이트로의 이동과 Enter가 따르는 입력이 각각 `데스크톱에서 승인 대기` 행(사이트, 끝나는 시각)이 되고, 대화·나를 기다리는 것 카드·목록 어디에도 답하는 단추가 없다. 폰이 그래도 보낸 답은 `unauthorized`로
  거절되고 승인은 그대로다.
- 데스크톱의 `거부`는 `사람이 거절했습니다.` 행이 된다. 240초(그 main 프로세스에서만 30초로 줄임)가 지나면 `데스크톱에서 답이 없어 시간 초과로 끝났습니다.` 행이 남고, 데스크톱과 폰의 늦은 답은 둘 다 `not-found`,
  사이트에 POST는 0건이다.
- 폰이 받은 것에 입력값이 없다: 앱이 받는 지점에서 읽은 소켓 메시지 315개(API 35)·322개(API 29), 그 가운데 승인을 실은 22개에서 입력값과 `/checkout` 모두 0건. 페이지, localStorage 6개, 앱 플러그인으로 읽은
  보안 저장소 5개, 앱 파일과 logcat도 0건이다.
- 나를 기다리는 것 카드는 336×114px이다. 끝나면 `wm`을 되돌리고(두 기기 모두 덮어쓴 값 없음) 에뮬레이터를 껐다.

## 계획과 달라진 것

- 보이지 않는 뷰는 `setVisible(false)`가 아니라 화면 밖 창에 둔다(숨긴 뷰는 클릭과 `capturePage`가 듣지 않았다, 측정).
- 제어 포트는 계획의 셋이 아니라 여섯이다. 거절 코드는 12가 아니라 17이다.
- payload: 스크린샷은 `url`이 아니라 `origin`을, 자동 확인은 `{ state, summary }`가 아니라 `{ origin, providerId }`를 담고 행 종류는 `browser-check`다.
- 비밀번호: 로컬에서만 가리는 것이 아니라 모든 입력값을 가리고, 비밀번호 칸은 허용한 외부 사이트에서만 거절한다.
- 주소 찾기에서 주소창은 빠졌고, AI 출력은 민감하지 않은 `command` 결과만 읽는다.
- 망 막기는 "도구가 붙었을 때"가 아니라 늘 켜져 있고, 응답 주소 확인은 허용한 사이트만이 아니라 로컬이 아닌 모든 이름에 적용된다. 로컬 페이지 안의 외부 프레임도 거절한다.
- 허용 목록은 safeStorage로 봉해 쓰고 시작할 때 한 번만 읽는다(계획에 없음, 보안 검수 B5).
- 계획의 `scripts/guard-in-app-browser.mjs`는 만들지 않았다. 파티션·`disableDialogs`·preload 없음·`openExternal`은 OS 테스트와 단위 테스트가 지킨다.

## 재지 못한 것

- **실제 외부 사이트.** 모든 페이지는 루프백 스텁이었고, 공개 이름은 그 실행에서만 공개 주소로 보이게 했다.
- 여러 턴에 걸친 설득, 전체 권한에서의 주입, DevTools와 `debugger`를 함께 쓰는 경우, 이 PC 밖의 화면 밖 창 렌더링.
- Codex code mode에서 입력값이 어디까지 드러나는지(스크립트 출력·로그).
- 패키지 EXE에서 브라우저 경로를 돌리지 않았다. `pnpm test:e2e:packaged`는 이 경로를 지나지 않는다. 성능 측정은 돌리지 않았고 설치 파일은 만들지 않았다.

## 남은 것

- 허용한 사이트의 DNS 리바인딩: 요청 전 이름 확인을 지나도, 응답이 시작될 때 주소를 다시 볼 때까지 첫 응답 하나는 페이지에 닿는다.
- WebSocket은 응답 주소를 알려 주지 않아 이름을 다시 풀어 보는 것뿐이다. 다시 보기 전에 되돌아간 이름은 지나간다. 다시 확인하는 층은 일부만 덮는다.
- provider 자신의 하위 에이전트(Claude의 Task 등)는 부모의 토큰과 권한으로 브라우저 도구를 부른다(보안 검수 B7). 앱은 그 호출을 부모의 것과 구별하지 못한다.
- 숨긴 글 거르기는 `clip-path`, `color:transparent`, 다른 요소에 가려진 글을 놓친다. 앱은 주입을 찾아낸다고 말하지 않는다.
- 페이지 스크립트의 `a.click()`이 사람의 실제 입력 1초 안에 일어나면 사람의 이동으로 통과한다. 그 페이지는 사람이 연 페이지로 다뤄져 허용 전까지 AI가 읽지 않는다.
- 입력값은 본래 사람의 메시지와 provider 자신의 세션 파일에 남는다(실제 실행에서 확인). 앱이 지울 수 없다.
- 같은 사용자로 도는 프로그램은 OS 키에 닿거나 예전 허용 목록 파일을 되돌려 놓을 수 있다.
- 첫 AI 사용 때 대화 패널이 아직 독에 없으면(새 대화의 첫 턴에서 도구를 곧바로 부를 때) 패널이 열리지 않는다. 도구는 돌고 대화 머리의 🌐로 연다. 캡처 실행에서 한 번 보였다.
- 좁은 패널에서는 페이지가 넘쳐 스크린샷에 내용이 잘릴 수 있다(사람이 보는 그대로, 위 결정). `browser_screenshot`의 설명은 아직 "1280 pixels wide"라고 해 패널 폭을 말하지 않는다.
- 시안 승인 뒤 생긴 글은 사용자가 본 적이 없다([목록](../overhaul/approvals.md#내장-브라우저-구현-중-정한-것-조정-작업자의-위임-판단-사용자의-결정이-아니다)).
